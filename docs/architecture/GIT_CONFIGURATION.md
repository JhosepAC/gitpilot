# Integración con Git y recuperación

## Descubrir e inspeccionar

- Escanear raíces elegidas por el usuario con límites de tiempo, profundidad y entradas. Excluir por componentes, evitar ciclos y omitir enlaces y junctions en el recorrido automático. Validar candidatos por Git, incluidos archivos `.git`, y diferenciar raíz de trabajo, Git dir efectivo y Git dir común. Identificar repositorios bare, submódulos y worktrees para el diagnóstico.
- Confirmar el contexto con `git rev-parse` e inspeccionar una lista explícita de claves con `git config`, incluyendo origen, ámbito y duplicados. Usar salida delimitada por NUL donde corresponda. Para identidad de commit, comprobar autor y committer con `git var`. Identificar Git no confiable o repositorio con ownership dudoso y mostrar error sin alterar `safe.directory`. [git rev-parse](https://git-scm.com/docs/git-rev-parse) · [git config](https://git-scm.com/docs/git-config)
- Inspeccionar configuración de sistema, global (HOME/XDG o archivo redirigido), local, worktree, includes y precedencia por orden. Detectar entradas efectivas de entorno o de comando en el contexto inspeccionado. Mostrar el archivo y ámbito concretos antes de autorizar.

## Materialización propuesta

1. Git carga una única referencia administrada al final del archivo global aprobado. Si existe `$HOME/.gitconfig`, usarlo. Si solo existe el archivo Git de XDG, usar ese. Si ninguno existe, proponer crear `$HOME/.gitconfig`. Si `GIT_CONFIG_GLOBAL` redirige la configuración o no se puede determinar la ruta normal con certeza, mantener diagnóstico de solo lectura en ese contexto. Conservar los bytes ajenos al cambio. El manifiesto activo apunta a perfiles inmutables versionados con nombres derivados de IDs.
2. Para repositorios ordinarios, emitir `gitdir:<raíz>/**/.git` desde la raíz más general a la más específica. Añadir al final las excepciones con Git dir exacto. Materializar el predeterminado bajo raíces registradas sin regla explícita. Canonicalizar y escapar los componentes literales del glob antes de serializar la subsección de Git. Usar coincidencia sensible a mayúsculas como base. Considerar `gitdir/i` solo cuando pueda comprobarse que la equivalencia del filesystem no amplía el alcance. [Inclusiones condicionales de Git](https://git-scm.com/docs/git-config/2.39.0#_conditional_includes)
3. Aplicar mediante esa inclusión cuando la expectativa sea representable. Una fuente local ajena que prevalece sigue intacta al aplicar reglas generales. Para cambiarla, preparar una edición separada de las claves exactas y del archivo local confirmado. Si una clave viene de un include compartido, un ámbito superior al alcanzable o un destino cuyo impacto no puede verificarse, ofrecer diagnóstico y conservarla.
4. El sufijo `/**/.git` evita los metadatos habituales de worktrees vinculados y submódulos. Git compara la ruta de metadatos, por lo que un bare cuyo directorio se llame `.git` o un Git dir separado con esa forma todavía puede coincidir. Mostrar estos límites en la vista previa. Para una regla nueva, verificar repositorios conocidos y worktrees vinculados y bloquear si afecta a una topología fuera del alcance admitido. Las topologías especiales, rutas de red o aliases sin alcance verificable quedan en diagnóstico. Las reglas de carpeta admiten repositorios ordinarios futuros y las exclusiones siguen limitando el descubrimiento.

## Protocolo de escritura

1. **Plan.** Capturar revisiones, identidad de archivos y directorios, huellas, precedencia y efecto previsto. Mostrar diff filtrado, archivos y repositorios afectados, alcance en repositorios futuros y casos que conservarán valores existentes. Si hay un límite de simulación, exponerlo y requerir verificación posterior.
2. **Confirmación y preparación.** Ligar la confirmación al ID y huella del plan. Adquirir coordinación entre instancias y respetar los locks de Git. Revalidar rutas, dependencias, permisos y huellas bajo bloqueo. Ante un cambio externo, caducar el plan y volver a inspeccionar. Crear respaldos privados verificados y persistir el journal antes de alterar destinos.
3. **Aplicación.** Generar archivos inmutables y validarlos antes de activar sus referencias. Sustituir cada destino mediante una operación atómica en el mismo filesystem, con durabilidad comprobada según plataforma. Registrar las etapas y huellas esperadas antes de cada sustitución. Coordinar cambios de varios archivos con el journal y publicar referencias solo cuando existan los perfiles correspondientes. Repetir el mismo plan debe reconocer el resultado o pedir recalcularlo, sin duplicar inclusiones.
4. **Verificación.** Releer mediante Git los casos afectados, incluidos conflictos que se conservaron. Verificar los alcances y actualizar SQLite solo tras confirmar. Una verificación fallida activa recuperación.
5. **Recuperación.** Deshacer en orden inverso solo donde la identidad y huella actuales coincidan con el estado escrito por GitPilot. Eliminar un archivo originalmente ausente bajo esa misma precondición. Si existen ediciones ajenas, conservar respaldos y bloquear escrituras afectadas hasta resolverlas. Al reabrir, reconciliar operaciones interrumpidas. La restauración manual también requiere vista previa y confirmación.

## Vista previa de la fase 4

GitPilot lee una instantánea del inventario y genera un manifiesto candidato con las reglas de carpeta antes que las excepciones. Una raíz interior sin regla explícita hereda la regla de un ancestro antes de usar el predeterminado. Git evalúa los perfiles y el manifiesto en un directorio temporal privado de la aplicación. La simulación usa un archivo global temporal que incluye XDG y HOME en su orden normal y después el manifiesto candidato. Los includes relativos de la configuración original siguen resolviéndose desde sus propios archivos.

La comparación se limita a la configuración de identidad de repositorios conocidos y worktrees vinculados verificables. El presupuesto es de 80 comparaciones y 15 segundos para el recorrido de verificación. Una raíz sin escaneo completo, un entorno redirigido o una topología especial pueden reducir la cobertura. La simulación añade un nivel de inclusión y puede fallar en configuraciones que ya estén cerca del límite de Git. Las reglas de carpeta pueden alcanzar repositorios ordinarios futuros y rutas excluidas del inventario. Los resultados describen el momento de la consulta. La confirmación de escritura requerirá una nueva comprobación de archivos y revisiones bajo bloqueo.
