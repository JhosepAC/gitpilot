# Autenticación remota y firma

Alcance posterior a v0.1.0. El [ADR-004](../decisions/ADR-004-autenticacion.md) adopta GitHub App y Device Flow para la fase 6. La [especificación de GitHub](../architecture/GITHUB.md) concreta el registro y las entregas de implementación.

| Capacidad | Comportamiento previsto |
| --- | --- |
| SSH | Referenciar claves existentes y alias, detectar permisos y archivos faltantes, inspeccionar configuración y probar hosts de forma explícita. Validar host, opciones y cliente SSH. Respetar la comprobación de host y tratar conexiones de prueba como operaciones de red. Una edición de `~/.ssh/config` requiere diff, respaldo, confirmación, prueba y recuperación. |
| HTTPS | Detectar el mecanismo de credenciales del entorno y guiar al usuario con Git Credential Manager u otro helper compatible. Mantener las credenciales bajo ese mecanismo. Las pruebas activas requieren acción explícita y remotos permitidos. |
| Firma | Configurar referencias a claves de firma SSH/OpenPGP por separado. Diagnosticar formato, disponibilidad y configuración efectiva. No generar ni copiar claves privadas automáticamente. |
| GitHub OAuth | Conectar varias cuentas en el navegador, identificar por ID remoto y guardar tokens en el almacén del SO. Consultar perfil, organizaciones, repositorios autorizados, PR e issues. Gestionar expiración, cancelación, revocación y límites de API. |
| Inspector y pre-commit | Mostrar la cuenta autenticada solo cuando sea comprobable. La advertencia en pre-commit se instala voluntariamente y debe coexistir con hooks del usuario. El bloqueo exige habilitación explícita y la desinstalación restaura el estado autorizado. |

El flujo de escritorio elegido es Device Flow con el Client ID público de una GitHub App. Los permisos de lectura se definen en el registro. La implementación respetará los intervalos de consulta, la expiración y la cancelación, y verificará la cuenta antes de persistir la credencial. [Autorización de usuario de GitHub Apps](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)

Usar almacenes seguros por plataforma, con Windows Credential Manager y Linux Secret Service como candidatos. Si no están disponibles, explicar cómo habilitarlos y evitar persistir secretos. Al desconectar, retirar el secreto local y exponer si la revocación remota quedó pendiente. El acceso al API de GitHub, la clave usada para Git remoto y la identidad de commit pueden pertenecer a perfiles diferentes.

## Inspector local

- El Inspector revalida la ruta y el Git dir del repositorio registrado. Lee el índice sin bloqueos opcionales ni monitores externos. Para contar cambios sin preparar, Git compara el árbol con el índice original desde un Git dir temporal con una lista cerrada de ajustes. Los filtros declarados en archivos rastreados, el índice no compatible o un resultado fuera del presupuesto dejan ese conteo sin verificar. [Estado de Git](https://git-scm.com/docs/git-status)
- Los destinos de lectura y envío provienen de Git y tienen en cuenta sus reglas de reescritura. A la interfaz llegan el nombre del remoto, el transporte y el host. El usuario, contraseña, ruta, consulta y comando de transporte permanecen fuera de la respuesta. [Remotos de Git](https://git-scm.com/docs/git-remote)
- En SSH se comprueban el cliente en PATH, la presencia de un socket anunciado y los archivos predeterminados o referencias simples dentro de `~/.ssh`. Los alias literales se muestran como indicios del archivo de usuario. La revisión de una ruta configurada resuelve las directivas compatibles con OpenSSH. El diagnóstico local de archivos de clave se limita a metadatos y los permisos Unix se muestran como indicios. [Configuración de OpenSSH](https://man.openbsd.org/ssh_config)
- Para HTTPS se clasifican los helpers generales, se respeta el reinicio de la lista y se indica cuando hay reglas por URL. Los argumentos de los helpers y las credenciales permanecen en el mecanismo configurado. Para firma se muestra la preferencia, formato y tipo de referencia. Una referencia SSH a un archivo simple dentro del directorio local `.ssh` admite comprobación de presencia. [Configuración de Git](https://git-scm.com/docs/git-config)

Las cuentas remotas y la posibilidad efectiva de autenticar o firmar requieren una prueba explícita. El Inspector local prescinde de conexiones, ejecución de helpers, consultas a agentes, programas de firma y escritura de configuración.

## Comprobaciones explícitas

La confirmación liga el repositorio, el destino o la clave y la modalidad. SSH y HTTPS consultan `HEAD` con `git ls-remote` desde un contexto temporal. Los resultados acreditan la respuesta del remoto al intento de lectura. La identidad de la cuenta remota se comprueba por separado. [Lectura de referencias remotas](https://git-scm.com/docs/git-ls-remote)

- **HTTPS.** La lectura anónima y la lectura con credenciales usan TLS verificado y descartan redirecciones. Git aplica el orden de helpers, los reinicios de lista y las reglas de usuario y ruta por URL. La prueba acepta los nombres `manager`, `manager-core`, `cache`, `wincred` en Windows y `libsecret` en Linux. GCM usa Windows Credential Manager o Secret Service, según la plataforma, en modo no interactivo. La búsqueda se detiene al llegar a un helper personalizado o con argumentos. La prueba usa `credential fill`, pasa la credencial en memoria para la solicitud HTTPS y prescinde de los comandos `approve` y `reject` de Git. Admite credenciales Basic de los repositorios de lectura en GitHub, GitLab y Bitbucket. [Protocolo de credenciales de Git](https://git-scm.com/docs/git-credential), [almacenes de GCM](https://github.com/git-ecosystem/git-credential-manager/blob/main/docs/credstores.md)
- **SSH.** La prueba directa abre una conexión sin cargar el archivo de usuario. Para la ruta configurada, OpenSSH resuelve una copia temporal de las directivas admitidas del archivo de usuario, con alias, puertos, archivos de identidad, certificado y hosts conocidos, inclusiones literales bajo `~/.ssh` y un salto `ProxyJump`. La revisión muestra el host y puerto resultantes y el salto cuando existe. El cliente exige claves de host conocidas en cada conexión y desactiva su actualización. El destino final debe pertenecer a GitHub, GitLab o Bitbucket, incluidos sus hosts SSH alternativos. Los glob de `Include`, las cadenas de saltos, `Match`, `ProxyCommand` y los clientes personalizados requieren revisión manual. [Configuración de OpenSSH](https://man.openbsd.org/ssh_config), [host SSH alternativo de GitHub](https://docs.github.com/en/authentication/troubleshooting-ssh/using-ssh-over-the-https-port)

- **Firma.** La prueba SSH usa una clave pública configurada directamente o un archivo `.pub` simple del directorio SSH de Git. La prueba OpenPGP requiere una huella o un ID largo en `user.signingKey` y GnuPG disponible. Usa el llavero local, sin cargar opciones de `gpg.conf`, solicitar una frase de paso ni recuperar claves por red. Ambas modalidades firman un desafío temporal y verifican su integridad. Los archivos del desafío se eliminan al terminar. [Firma con ssh-keygen](https://man.openbsd.org/ssh-keygen), [opciones de GnuPG](https://gnupg.org/documentation/manuals/gnupg/GPG-Configuration-Options.html)

## Hook pre-commit

La instalación exige un repositorio ordinario, una identidad esperada y la ruta de hooks predeterminada libre. GitPilot conserva los hooks existentes y los contextos con `core.hooksPath` personalizado. El modo inicial emite un aviso y el bloqueo exige selección y confirmación. La identidad revisada queda en el script hasta retirarlo e instalar una nueva versión. La retirada usa el journal y comprueba la identidad y huella del archivo. Ante una edición externa, Actividad presenta el destino como recuperación pendiente. [Hooks de Git](https://git-scm.com/docs/githooks)
